# 上传项目与运行环境

更新：2026-11-15。

## 正常使用流程

运行 `scripts/start_local.ps1` 后打开 `http://127.0.0.1:5173/#/`。

1. 在“新建任务”上传自己的项目 ZIP，必要时指定压缩包中的项目子目录。
2. 检查测试环境与验收范围，填写本次修复的问题、预期行为和需要保留的约束；提交后进入该任务的执行页面。
3. 上传项目在模型修改前执行基线测试；修复后由程序独立执行最终验收。任务页提供真实测试前后对比、执行日志、代码差异和原始测试查看入口。
4. 成功修复并保存原始经验后，系统自动登记持久化比较任务。同仓库检查等价规则和冲突；不同项目选取已有经验归纳共同规则，并独立复核。无需另行启动合并。
5. 在“经验记录”的“自动比较与合并”区域，直接对照本次原文、已有经验和合并后的规则，查看适用条件、业务约束、逐字引证及拒绝原因。下方处理冲突后，决定与依据自动同步到对照区域。任务结果中的经验链接会定位本次经验。

项目、运行设置、任务及经验均持久保存。页面刷新读取已有任务，不会重新提交修复。修改已上传项目的测试配置会产生新配置版本，不改变运行中的任务。

产品使用统一的 `/api/projects/upload`、`/api/tasks` 和 `/api/experiences` 工作流。“跨项目实验”页面及其 `/api/experiments`、`/api/experiment-materials` 专用接口已移除；旧页面地址通过通用路由回到首页。历史工程研究记录继续保存在仓库报告和脚本中，不参与应用启动或正常任务调度。

## 自动比较的运行规则

- 原始经验和比较任务在同一 SQLite 事务中提交。后台使用持久队列、租约令牌和心跳；服务重启可继续待执行工作，过期执行者不能覆盖新结果。合并失败与修复失败分别记录。
- 同仓库复用现有规范规则、完整等价组和条件/兼容域检查；保存多份原始经验和独立测试证据，模型引用按已确认的等价组去重。不同业务约束不会被强行拼成一份可互换的项目补丁。
- 不同项目使用 SQLite FTS5 候选排序，并补充最近 200 条同语言来源；再按错误类型和时间排序。本轮最多深入比较 5 条候选，页面显示候选总数、选中数与未比较数，不将未比较来源当作已判定无关。历史记录只作新经验的候选，不在启动时自动付费重跑历史研究。
- 跨项目共同规则必须有每份原文的逐字引用，经过独立复核，并完整保留各业务的约束与证据；它保存在正式经验库的产品命名空间。同仓库原始规则仍保持各自作用范围，跨仓库自动注入仍遵守原有通用经验发布与目标验证规则。
- 待整理、待审阅或已暂停的来源不能生成有效共同规则。冲突处理后自动重新检查来源资格；确认停用的来源会明确显示为保留原记录、不合并。撤销决定或停用来源后，历史合并立即显示为暂停，不能继续显示为当前有效合并。
- 比较与复核失败后停止自动付费重试。“重试未完成的比较”只重试失败比较，不重跑修复、不改写原经验、不重复已经完成的模型决定。请求重试和页面刷新不会重复登记同一来源对。模型比较过程中发生中断时保留记录并要求明确重试。
- 新增只读接口 `GET /api/experiences/automation`，支持语言、仓库、范围、经验 ID 与分页筛选；`POST /api/experiences/automation/{experience_id}/retry` 用于明确重试。页面每 5 秒读取变化，不通过读取接口触发模型调用。
- 所有模型调用复用运行中的应用 Settings 和本项目选定的 `.env`，不会自行读取其他仓库配置。每个候选至多一次归纳和一次复核；失败后的主动重试另计。

## 上传和运行环境

ZIP 上限 64 MiB；解压后总量 256 MiB、10000 条目、单文件 10 MB。拒绝目录穿越、盘符、Windows 设备名、重复/大小写冲突条目、符号链接、加密与特殊文件。凭据、Git、依赖目录不进入修复副本。原始测试和构建文件只读；显式选择的非标准命名测试文件也只读。

| 语言 | 识别标记 | 验收方式 | 需要的环境 |
|---|---|---|---|
| Python | pyproject.toml / pytest.ini / setup.cfg / setup.py | pytest + 新建 JUnit 报告 | 可选择已安装依赖的 Python 解释器 |
| Java | pom.xml | Maven clean test + Surefire XML | JDK 和配置的 Maven |
| Go | go.mod | go test -json -count=1 -mod=readonly ./... | Go 工具链及依赖可用 |
| C++ | CMakeLists.txt | configure → build → CTest --output-junit --no-tests=error | CMake、CTest、C/C++ 编译器；可选 Ninja |

Go 不使用缓存测试结果，不把编译失败、零测试或截断 JSON 视为通过。C++ 每次生成新报告，构建目录位于模型工作副本外。Windows 子进程保留系统缓存路径等必要变量，仍不继承模型凭据。

Python 上传时可携带 `.agent-upload.json`：

```json
{
  "task_description": "说明问题和需要保留的行为",
  "runner_config": {
    "python_version": "3.10",
    "requirements_file": "agent-requirements.txt",
    "python_paths": ["src"],
    "test_targets": ["tests/test_feature.py"],
    "pytest_plugins": [],
    "deselect": [],
    "timeout_seconds": 300
  }
}
```

`python_version` 和 `requirements_file` 可省略。若提供精确 `package==version` 清单，系统仅通过本机虚拟环境元数据匹配版本与依赖，不执行上传包来探测。找不到完整匹配时，需在页面选择已准备的环境。ZIP 不能指定本机解释器绝对路径。所有设置可以在页面检查；修改后生成新配置版本，不改变已经排队或运行的任务。仅修改上传说明不改变源码对应的仓库身份，经验和任务仍可按实际源码来源追踪。

不自动安装上传项目的任意依赖，也不支持任意 shell 命令。目前 C++ 针对 CMake/CTest，Java 针对 Maven；Gradle、任意 Makefile、无测试单文件和混合语言根目录不在本轮范围，可为单个子项目选择根目录。文件边界和子进程控制不是容器沙箱，面向本机可信项目。

Go/C++ 的经验范围目前保守保留到文件级，尚未接入相应 Tree-sitter 语法的函数级定位；因此范围有交集时可能需要更多人工冲突审阅，不宣称与 Java/Python 的符号定位覆盖一致。

## 验证与研究记录

自动化回归通过两次真实 ZIP 上传和常规 `/api/tasks`，使用受控模型响应分别修改生产代码，实际执行 pytest，验证失败→通过、自动比较与归纳、原始经验不变、业务边界保留及重启读取。另验证非同文的同仓库规则合并、冲突决定与撤销、候选数量限制、拒绝与失败、显式重试和过期租约。前端验证普通经验页直接呈现前后对照、轮询更新、冲突处理记录及暂停后的结果。模型响应是测试替身，不能当作真实模型效果。

已有真实执行验证：Go 与 C++ 都完成编译测试失败→修改生产代码→测试通过；完整 pytest 缺陷工程的 302 项验收复现 40 项失败，Sphinx 的 148 项验收复现 10 项失败，均无收集错误。原始输出保存在 `.cache/upload-engineering-validation/`。历史模型修复与经验合并结果见 [真实工程研究报告](reports/knowledge-remediation-2026-11-14/real-engineering-merge.md)。

如需离线复现工程研究，可按 `benchmarks/engineering-merge/README.md` 准备原始源码，并运行 `scripts/package_engineering_uploads.py` 生成 ZIP。将 ZIP 当作普通项目在首页上传即可；产品不提供指定工程的下载入口或特殊修复通道。

## 官方方案依据

- [Starlette 请求流](https://github.com/Kludex/starlette/blob/main/docs/requests.md): 以有界请求流接收 ZIP，先限制上传体积，再校验条目与解压大小。
- [Go command](https://pkg.go.dev/cmd/go): 使用 `go test -json` 读取结构化事件，`-count=1` 禁用测试结果缓存。
- [CTest](https://cmake.org/cmake/help/latest/manual/ctest.1.html): 使用 `--output-junit` 和 `--no-tests=error` 获取可审计测试结果。
- [pytest usage](https://docs.pytest.org/en/stable/how-to/usage.html): 显式节点选择、插件和 JUnit 输出；不接受模型随意缩小最终验收范围。

当前流程验证（2026-11-15）：后端全量 677 项通过、1 项跳过；自动流程模块补充后共 11 项通过；前端 140 项通过，类型检查与生产构建通过。正式库的比较任务从新保存的经验开始登记，页面不会导入历史研究结果冒充本次自动合并。

最终验收已通过但经验提取失败或未执行时，可在原任务结果中点击“重新提取经验”。系统核对保留源码与结束时快照后，用原始修复记录和最终测试证据调用模型，不重新执行代码修复。达到决策额度的任务仍保留“已停止”状态及原因；有效经验保存后照常进入后台自动比较。重复点击不会重复提交正在运行的提取；服务重启后需要手动重试中断操作。

不同上传版本中具有相同已落地代码符号的经验，也会进入冲突检查：模型判断共同适用条件与互斥要求，程序核对双方原文，再独立调用模型复核。真实冲突通过现有审阅流程暂停相关规则和失去来源支持的共同原则；经验页显示双方引文、共同条件、独立复核及处理前后状态。采纳指定来源是可审计的审阅决定，系统不会仅按时间新旧自动选胜者。比较失败可在经验页单独重试，已完成的修复与比较不会重跑，失败尝试审计保留。

当前跨上传冲突检查仅覆盖本轮选中的最多 5 条候选，且要求精确共享符号；路径重命名、同义但不同符号、尚无符号定位的语言可能漏检，不代表未选中的经验都没有冲突。

确认冲突后，普通后台队列会自动核对双方冻结源码和测试证据。支持移植的 Python 函数会在独立副本中完成两次原上下文验证、四次交叉验证，全部使用各来源原本登记的测试。唯一实现通过双方测试且另一方重复复现原始缺陷时，系统自动采纳该来源；双方各自有效、交叉却失败时，系统自动隔离冲突规则。原始记录始终保留，经验页直接展示每次测试、前后状态和“系统自动保存决定”。

无法可靠交换实现、验证中断、测试不稳定、结果无法区分或其他证据不足时，页面会说明原因并请求用户确认。自动验证期间不要求手动选择；原有审阅入口继续支持最终确认或撤销。当前跨语言的修复支持与自动交叉验证范围不同：Java/Go/C++ 可以修复和生成经验，但其冲突函数移植暂不自动执行。自动结论只覆盖登记的测试；隔离意味着暂停相互矛盾规则的自动复用，不代表某条原始经验被删除。

经验记录页默认以卡片展示解决方案、适用状态、来源数和验证数；合并卡片直接显示“多份来源 → 一条知识”，展开查看原文和合并后对比。“合并与冲突”查看处理过程，“原始记录”保留完整来源。正常管理按钮“整理历史经验”将旧合格记录补入自动比较队列；缺失结构化证据的旧笔记仅归为待验证经验组，不提高信任或自动注入修复。每次最多比较 10 份旧笔记，页面显示剩余数量；重复提交已完成扫描不会重复付费，失败可显式重试。真实结果与截图见 [经验库改版实录](reports/knowledge-remediation-2026-11-15/experience-library.md)。
