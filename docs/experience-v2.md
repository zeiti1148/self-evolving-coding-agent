# 复杂经验、多异常与项目仓库

## 经验的粒度

一条经验表示一次已验证的修复知识。`issues` 保存多个问题，各自包含异常类型、根因、方案和相对文件位置，数组顺序就是推荐修复顺序。`applicability` 记录规则成立的前提，避免把某个业务的默认值直接套用到其他业务。原有摘要、根因、方案、标签字段仍保留，旧九列数据库自动兼容迁移。

程序在独立最终测试成功后绑定 `evidence`：来源任务、真实工具调用 ID、实际测试执行器和测试计数。模型负责归纳知识，程序负责填写仓库、语言、版本、测试事实和来源。Java 使用 Maven，Python 使用 pytest。

## 保存、检索和合并

新任务接收服务器登记的语言、仓库 ID 和源码快照指纹，优先检索同仓库经验，再选对应语言的通用经验。多种异常通过 `issues` 一起匹配。测试暴露新的异常后，Agent 更新检索结果，后续模型请求携带对应经验。最终测试仍有失败且决策预算未耗尽时，失败明细回到上下文，继续修复。

经验合并采用“选择记录—预览—确认生成新记录”。合并须保持语言、仓库范围和适用条件兼容；同一位置的冲突方案、互相矛盾的修复顺序会在预览中说明。原记录保留，`merged_from` 可追溯直接来源，结构化测试证据保留原任务和调用 ID。相同来源集合重复提交返回同一结果。检索使用合并后的有效记录，不重复注入已被替代的来源。

合并是确定性的知识整理，不额外调用模型改写方案。互斥或文字不同、需要语义裁决的规则先保留分开，交由团队检查。

## 项目仓库登记

服务器配置是项目路径的唯一来源，浏览器只提交登记 ID。通过 `scripts/register_project.py` 登记本地可信仓库中的 Java 或 Python 项目，设置 `PROJECT_REGISTRY` 后重启后端。多个子项目需要共享经验时使用同一个稳定 `repository_id`。登记项目根目录必须有与语言一致的唯一构建标记：Java 为 `pom.xml`，Python 为 `pyproject.toml`。混合仓库分别登记对应子目录。

来源版本由 Git HEAD（若可用）和实际工作副本初始文件哈希组成。源码本地未提交的变更也反映在快照哈希中。仓库 A 的专属经验不进入仓库 B；通用经验另有 `global` 标识。

Python 任务在服务器提供的解释器内执行 pytest，依赖预先安装；工具不执行任意安装命令。测试配置、测试文件和依赖清单不可由 Agent 修改。pytest 报告位于模型不能写入的独立目录，每次使用新文件；零测试、跳过、超时和框架故障不产生通过结论。

## API

| 接口 | 用途 |
| --- | --- |
| GET `/api/projects` | 获取可提交项目、语言、仓库 ID、版本与任务示例，不返回磁盘路径 |
| POST `/api/tasks` | 按 `source_project` 提交任务，兼容旧请求 |
| GET `/api/tasks/{id}`、`/steps` | 状态、最终结果及运行中工具步骤 |
| GET `/api/experiences` | 保留分页数组响应，新增 `language`、`repository_id`、`scope` 可选过滤 |
| POST `/api/experiences/merge-preview` | 请求 `{experience_ids:[...]}`，返回兼容性、冲突和拟生成记录 |
| POST `/api/experiences/merge` | 同一来源集合幂等生成合并经验，冲突返回 409，缺失来源返回 404 |

## 验收

`scripts/acceptance_v2.py` 默认使用测试专用脚本模型，通过真实 API、工作副本、Maven、pytest 和 SQLite，验证部分修复失败后继续处理、全部测试通过、三问题经验、合并幂等、合并结果实际进入后续模型请求和仓库隔离。

`--live` 使用 `.env` 指定的模型，分别修复两个语言案例。报告按模式独立保存到 `.cache/acceptance-v2/<run>/report.json`，包含原始失败、结果、真实模型审计、修改文件、经验和合并记录。合并验收将一条已验证经验明确拆分为两个组件记录，再合并检查；这些组件不是额外模型修复任务。历史 24 项实验不混入本轮结果。
