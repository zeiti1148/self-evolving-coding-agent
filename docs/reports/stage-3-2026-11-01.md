# 阶段三：复杂任务修复与经验演进（2026.10.26—2026.11.01）

本文可接在已有“阶段二：核心功能集成与经验复用验证”之后。阶段一、二的衔接依据为用户从飞书粘贴的原文；原飞书链接要求登录，本次未读取其完整页面。以下成果以仓库代码和实际验收记录为依据，不将计划写成已完成事项。

## 一、主要完成工作

1. **复杂任务与多语言支持。** 在 Java/Maven 修复流程上增加 Python/pytest，扩展跨文件、组合异常和输入边界样例。早期 V2 完成两种语言的三模块组合异常修复；V3 增加 checkout 来源与 booking 目标四个独立仓库，来源各含 18 项测试，目标各含 12 项不同业务条件的测试。
2. **可靠性优化与基线保留。** 延续任务持久化、连接处理、工作副本隔离、受控工具和独立最终测试。在 `experience-collaboration-v3` 分支增量开发，保留原有工作区设计与计划。M0 后端 392 项、前端 78 项基线测试通过。配置的运行数据库不存在，因此如实记录无库可备份，另交付经过测试的 SQLite 一致性备份脚本。
3. **一次修复产生多条经验。** 将经验提取扩展为一次模型响应返回 1–5 条具有独立用途和适用条件的经验，并兼容旧单经验结果。复杂来源在一次成功修复后直接产生文本处理、整数处理和集合选择三条经验，没有复制或人工拆分数据库记录来增加数量。
4. **真实证据与原子保存。** 模型只提供知识内容，程序将经验关联到本次修复的真实最终测试、仓库和来源版本。整个批次在一个 SQLite 事务中保存，相同任务和内容重复提交返回原有 ID。实际注入第二条保存失败后整批回滚，修复成功与经验保存失败分别展示。
5. **统一仓库隔离。** 单 Agent、多 Agent 各角色及实验检索共用同一规则，只允许当前仓库专属经验和同语言、条件符合的已发布通用经验进入模型请求。旧通用记录默认待审阅，合并来源和旧发布版本保留查询但停止注入。发布前，两个目标仓库均未收到来源仓库的专属经验。
6. **完善合并与来源追踪。** 增加语言、仓库、状态、适用条件、能力、修复规则和顺序的冲突检查，支持合并预览、重复请求去重、并发冲突和来源图。原始记录保留，同一来源集合重复合并返回同一结果，重叠来源不能被并发消费两次。
7. **显式通用发布与跨仓库复用。** 项目经验经过通用化预览、人工编辑和显式发布后生成新的通用记录，保留原始记录与来源关系。公共注入内容省略原仓库、文件路径及原始验证文本。Java、Python 的目标任务均实际收到已发布通用经验，并按照目标自身的默认值、范围和拒绝策略通过 12 项测试。
8. **产品运行时多 Agent 协作。** 实现独立上下文中的诊断、修复和复核角色。两个诊断调用读取同一只读快照，修复角色提交修改提案，复核通过后由程序检查路径、版本及文件哈希并统一应用。角色共享步数和时限，最终成功必须由程序独立执行 Maven/pytest 确认。
9. **前端完整联调。** Vue 增加 single/multi 模式、角色过程、多条经验链接、仓库与状态筛选、合并预览、通用发布和来源追踪，保留原有深浅色风格。真实浏览器完成来源修复、合并发布、目标复用和单模式兼容流程；API 重启后，任务、角色事件、经验和来源图保持可查询。
10. **异常场景与回归验收。** 补充跨仓库误注入、批次保存失败、并发合并、过期提案、预算耗尽、角色异常和重启恢复。2026-10-31 全量后端 498 项、前端 87 项测试通过，构建与接口联调通过。V3 脚本验收 13 个任务均符合预期，其中包括预期停止、预期失败及修复成功但保存失败的负例；V2 兼容验收 4 个任务通过。
11. **交付材料整理。** 交付代码、备份与验收脚本、机器可读报告、演示步骤和阶段汇报材料。本次将新成果提交至 `experience-collaboration-v3` 分支供团队审查，主线集成另行进行；实际提交与推送信息见本次交付记录。

## 二、阶段性成果

形成了“复杂任务修复、独立测试、一次提取多条经验、原子保存、同仓库检索、可追溯合并、显式通用发布、同语言跨仓库复用”的工程流程，并接入独立诊断、修复提案和复核角色。前端能够查看对应过程与结果，任务和经验可以持久化查询。

本阶段的证据需要分开解释：

- **V2 历史真实模型记录：** 2026-10-26 报告记录 Java、Python 组合修复及 Python 合并复用三次真实模型任务，每次 12 项最终测试通过。当时合并验收使用拆分来源，不作为 V3“一次自然产生多条独立经验”的证据。
- **V3 工程验收：** 2026-10-31 使用脚本模型替代模型响应，实际运行 API、SQLite、代码工具及 Maven/pytest，验证多经验、隔离、发布、协作与异常处理。不能据此认定真实模型的 V3 修复能力或经验语义质量已经验证。
- **尚未完成：** V3 环境缺少完整模型配置，真实模型验收为 `not_run`，调用次数为 0；“无经验、完整经验、精简经验”三组正式对照仍未完成。没有新的对照证据，因此不宣称 V3 提升成功率、减少耗时或节省 token。

## 三、下一阶段计划

以下是根据现有完成情况提出的下一阶段安排，并非原飞书文档已经批准的排期。

1. **完成团队复现与分支评审。** 以本次提交为固定版本，在另一台开发机复现安装、接口联调、V3 脚本验收和页面流程，核对历史 PR/分支的集成状态，再决定主线合并。
2. **补齐 V3 真实模型验证。** 配置模型后运行 `scripts/acceptance_v3.py --live`，先验证来源修复、多经验语义、合并后复用及发布前后目标任务。记录模型版本、实际请求引用、最终测试、token、耗时和失败原因，不将脚本结果混入真实模型结果。
3. **落实三组经验对照。** 实现并检查无经验、完整经验、精简经验三个条件，使用相同模型、相同任务预算、固定测试和冻结经验库。训练任务与评估任务隔离，条件交替执行并保留重复试验。分别统计检索、实际注入、最终成功、工具调用、已报告 token 和耗时。
4. **扩充复杂业务样例。** 在现有 Java/Python 样例上增加跨文件依赖、相同异常但不同业务策略、能力相似却不适用等任务，检查错误经验是否被排除、目标合同是否保持。继续覆盖并发、版本过期和重启场景。
5. **形成优化结论与答辩版本。** 仅在对照数据支持时调整匹配排序、经验压缩和上下文长度；说明收益与成本。整理失败案例、运行限制、三人分工、演示录像及答辩说明，形成可由团队复现的最终材料。
