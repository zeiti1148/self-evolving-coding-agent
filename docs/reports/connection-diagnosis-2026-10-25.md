# 模型连接故障定位与修复记录

原模型客户端使用 HTTPX 默认配置，会隐式继承终端中的 `ALL_PROXY`。本机该变量指向 `socks5://127.0.0.1:7890`；实际连接跟踪确认请求先进入 SOCKS 代理，本地代理控制器显示 DeepSeek 连接被送到海外出口。项目没有明确选择该路径，却依赖了其稳定性。

## 复现证据

在原代码提交 `07290d6` 上，使用相同服务地址、相同证书校验和交错顺序，只改变是否继承环境配置。每次新建客户端，保留全部请求结果。诊断不改系统代理、不关闭证书校验，也不执行模型返回的工具。

| 批次 | 继承代理 | 直连 | 用途 |
| --- | --- | --- | --- |
| 初步 GET 连通性 8 对 | 8/8 建连成功 | 8/8 建连成功 | 不带密钥；HTTP 401 表明已到达认证层 |
| 首次决策 6 对 | 6/6 HTTP 200 | 6/6 HTTP 200 | 映射空值和 Greeting；使用前次冻结经验，仅请求第一轮决策 |
| 扩展 GET 连通性 24 对 | 19/24 建连成功 | 24/24 建连成功 | 不带任务文本或密钥，复现传输故障 |

扩展批次中代理路径的 5 次失败均满足：TCP 连接成功、SOCKS 建立成功，随后 `socks.start_tls.failed`。异常链为 `httpx.ConnectError → httpcore.ConnectError → ssl.SSLEOFError`，TLS 原因为 `UNEXPECTED_EOF_WHILE_READING`，即握手期间连接被提前关闭。失败时尚未发送 HTTP 请求头和正文；它不是认证拒绝、测试断言失败或模型不理解案例。紧邻的直连请求均成功。

所以，可复现的故障点已定位到环境代理所选路径上的 TLS 握手中断。操作性原因是项目隐式继承了不稳定的代理路径；目前没有足够证据进一步指认代理出口、中间网络或服务端中哪一个组件主动关闭了 TLS。旧审计没有保存异常链，不能逐条声称此前每次 ConnectError 都已回溯确认。

## 为什么两次出现在同一任务

历史两轮在其他案例上也分别出现过可恢复的 ConnectError；并非只有映射空值案例失败。两轮均按固定案例顺序执行，而该任务碰到连续三次建连失败，耗尽原有重试上限。此次用不含任何案例内容的 GET 就复现了同类异常，同一映射任务的首次模型请求也在诊断中成功。证据不支持把连接错误归因于该 Java 文件、经验内容或检索归一化；不能仅凭同一序号重复失败推断更具体的时间触发条件。

## 修复与验证

新增 `LLM_TRUST_ENV`，默认 `false`，使模型请求直接连接所配置服务。需要环境代理或自定义 CA 的环境可显式设置 `true`，并使用 HTTPX 的 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY`、`NO_PROXY` 和 `SSL_CERT_*`。本机只设置项目自己的 `.env`，没有更改系统或代理软件配置。两种模式均保持 HTTPS 证书验证。

新增有界连接审计：记录 TCP、SOCKS、TLS、HTTP 阶段，以及异常类型、整数错误码和白名单 TLS 原因；不保存异常原文、地址参数、HTTP 头或请求正文。实验报告记录连接策略与传输模块、配置模块的源码哈希。重试仍为最多三次，只针对建连失败；读取超时不重试，失败任务不被改写为成功。

测试以本地真实 HTTP 目标和代理验证默认直连及显式代理选择；另用本地套接字接收 ClientHello 后关闭连接，验证真实 TLS EOF 的阶段、异常链和三次上限。脱敏测试检查异常消息、请求头和跟踪数据不会进入审计。

完整修复后再单独运行三项训练和 24 项正式对照，结果记入实验总报告。上述诊断请求不混入正式成功率或 token 统计，前次失败记录保留。
