## 漏检与后续修复

原始训练模型把 error_type 写成“ArrayIndexOutOfBoundsException caused by out-of-bounds array index access”和“NumberFormatException and missing port-range validation”。存储合法，但与精确类别检索不相等。因此 range-end 和 parse-count 的四次经验开启任务没有收到参考，comparison_valid 为 false；不能把这些任务称为已接收经验的对照。

9012108 将异常字段归一化为 Java 简单类名，并让提取提示要求解释写入 root_cause。单测证明带解释或全限定名称能重新检索到。随后以 retrieval-check 启动新的三个训练任务和两个定向任务，五项全部修复通过，三类训练经验均能检索，两个目标任务均在成功模型请求中实际收到对应经验。原始冻结库和第一轮记录没有被改写。

## 结论与复现

当前证据证明真实修复、持久化和经验注入链路可运行，也发现并修复了检索键质量问题。两组修复均为 12/12，不能宣称成功率提升；应结合命中子集与调用、用量分析，不能把小样本耗时差异解释为显著加速。归一化后的完整 24 任务复测仍留在下一阶段，定向验证仅证明两类漏检已解决。当前简单案例存在成功率上限，需要更有区分度的测试集。

复现第一类实验：`.venv/Scripts/python.exe scripts/experiment.py --live --stage all`。复现归一化定向验证：`.venv/Scripts/python.exe scripts/experiment.py --live --stage retrieval-check`。两者均会调用真实模型；不带 --live 只打印规模，每次运行创建独立目录。

可审查的逐任务指标、请求审计、完整本地报告路径及 SHA256 见 [evaluation-evidence.json](evaluation-evidence.json)。新脚本在启动时记录 Git HEAD、dirty 标志及关键源码哈希。第一轮代码依据执行记录追溯为 core/llm@6f1ac6e、experiment@424565a，该标注不是脚本原生采集。定向验证对应的准确版本保存在 JSON 中。

本机原型的任务预算是协作式预算。同步 HTTPX 空闲超时尚不能强制中断持续缓慢的响应头或同步 DNS；独立请求隔离和硬取消待后续评估。CI 使用额外步骤与 job 时限。系统不是公网代码执行沙箱。
