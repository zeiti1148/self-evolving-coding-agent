## 漏检与后续修复

原始训练模型把 error_type 写成“ArrayIndexOutOfBoundsException caused by out-of-bounds array index access”和“NumberFormatException and missing port-range validation”。存储合法，但与精确类别检索不相等。因此 range-end 和 parse-count 的四次经验开启任务没有收到参考，comparison_valid 为 false；不能把这些任务称为已接收经验的对照。

9012108 将异常字段归一化为 Java 简单类名，并让提取提示要求解释写入 root_cause。单测证明带解释或全限定名称能重新检索到。随后以 retrieval-check 启动新的三个训练任务和两个定向任务，五项全部修复通过，三类训练经验均能检索，两个目标任务均在成功模型请求中实际收到对应经验。原始冻结库和第一轮记录没有被改写。

## 结论与复现

归一化后的完整复测已经完成，检索键问题在本轮恢复到 12/12 命中。两组最终成功率均为 91.67%，各一项失败来自网络链路，不能把这种故障归因于代码修复能力。经验送达与效果提升是不同问题：本组简单案例尚未显示成功率改善，双方成功配对的决策轮数均为 50、工具调用均为 63，报告 token 增加 12.22%。

十个成功配对中，开启组总耗时少 10.224 秒；关闭组与开启组未成功请求的等待分别为 21.053 与 10.427 秒，差 10.626 秒。该等待差与总耗时差同量级，不能把表面上平均快 5.75% 解释为经验加速。这里没有将等待时间相减后构造“无网络干扰”的实测时间，也没有估算未报告的用量或账单。

下一阶段重点是更有区分度的案例、精简注入内容和成本消融、稳定链路下的独立复现；不重复把已经完成的本轮复测列为待办。当前不扩大样本、不补跑两项失败，也不根据观察结果修改本轮协议。
