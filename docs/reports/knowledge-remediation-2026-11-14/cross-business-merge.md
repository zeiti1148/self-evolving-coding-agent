# 两个不同业务任务的自动经验合并实录

日期：2026-11-14。机器记录：[cross-business-merge.json](cross-business-merge.json)。

## 案例来源与独立性

这次预先创建两个不同的可运行业务项目，再由真实模型分别修复和提炼经验。它们是故意带缺陷的业务演示样例；没有把它们描述为生产事故。

| 项目 | 电商发票 | 教务成绩 |
|---|---|---|
| 源码 | `invoice.py#invoice_total` | `grades.py#publish_grade` |
| 输入 | 商品单价、数量、整单优惠券 | 分数、权重 |
| 计算 | 累加商品金额，再减优惠券并限制下限 | 加权和除以权重和，再判定及格和奖学金 |
| 输出 | 两位小数、CNY、商品行数 | 一位小数、及格与奖学金状态 |
| 任务 ID | `c07870ea-37f7-4e31-a7e5-c4615f286fa2` | `20e8cf33-2653-4234-b9c7-cae68f6f70e9` |
| 原经验 ID | `a2042a2f-8a52-4de8-aec7-cdd72903fbfc` | `248cdcfe-dc1d-4251-bc97-463c1301fdaa` |

两个任务采用独立 ChatClient、独立工作区、独立经验数据库，`use_experience=False`。所有修复请求的 `request_experience_ids` 均为空。第二个任务没有读取第一个任务的修复或经验；两份经验原文由各自的生产提取接口直接生成，未人工改写。

两项修复及提取各 6 次模型请求，原则归纳和复核共 2 次，总计 **14 次成功请求**。每次均记录了已确认配置文件 `D:\中级实训\self-evolving-coding-agent\.env` 的脱敏身份 `4f003362858407b3c4f55d13`。首次任务收尾遇到实验脚本访问不存在字段的错误；已保留成功的任务 A 结果并修复续跑逻辑，未重复请求任务 A。后续对照重放直接复用已落库原则，未新增 API 请求。

## 两段不同业务经验的原文

发票经验中的一条方案：

> 对单价和优惠券使用 Decimal 从字符串构造；逐行计算 Decimal(item["unit_price"]) * item["quantity"] 并累加，汇总阶段不做舍入，避免 float 中间值。保留负单价、非法数量等 ValueError 检查。

教务经验中的一条方案：

> 改用 decimal.Decimal 从原始字符串构造分数和权重，避免二进制浮点误差；计算加权和与权重和后，用 quantize(Decimal("0.1"), rounding=ROUND_HALF_UP) 得到最终一位小数发布分，并将该 Decimal 格式化为 mark。

两份完整经验还分别包含自己的业务限制、问题依赖及测试证据。完整原文、源码补丁和请求审计均在 JSON 中保留。

## 自动得到的共同原则

原则 ID：`4d9406fc-0bd6-5ee1-a78a-0303961c9ea3`，类型 `shared_principle`。以下为模型实际输出：

> 当修复目标是 Python 中以十进制字符串表示的数值（金额、分数等）计算时，共享的因果修复原则是：不要先用 float 解析或累加，也不要逐项或提前舍入；应使用 Decimal 从原始字符串构造参与计算的数值，保持汇总阶段未舍入，最后仅在业务指定的最终精度上使用 ROUND_HALF_UP 量化并输出。各业务必须自行提供自己的最终精度、阈值、币种、计算顺序、异常校验和返回契约，不能把某一业务的具体参数套用到另一业务。

自动归纳明确附带的适用条件包括：**业务要求中点向上 ROUND_HALF_UP，并允许汇总后一次性量化**。其他舍入模式或要求逐行舍入的业务，不在本原则的适用范围内。

保留的实例参数：

- 发票：精度 `0.01`，币种 `CNY`，先汇总再减整单优惠券，总额最低为 0，保留商品行数与非法订单异常。
- 教务：精度 `0.1`，成绩范围 0..100，权重大于 0 且无需和为 1，使用最终发布分判定 60/85 阈值，保留空成绩异常与返回字段。

程序检查了模型引用的支持片段确实逐字存在于原始子规则，然后发起一个新上下文中的复核请求。复核逐一确认两份来源支持该有条件原则、业务条件保留、未发现不安全泛化后，事务写入了 **1 条共同原则和 2 个来源实例**。复核使用同一提供商的另一次调用，不是独立第三方或形式化证明。

原始 2 份经验与 4 条项目子规则完全保留，指纹未合并，仓库和版本边界没有放宽。普通项目规则比较仍返回 `different_scope`。新增流程把共同修复原则保存于明确指定的实验命名空间，不自动发布为全局补丁，也不自动注入其他项目。

## 真实行为与破坏性对照

两项任务分别增加 2 项独立用例，未提供给修复模型。正确补丁和错误精度对照均运行同一组完整测试。

| 实际运行 | 电商发票 | 教务成绩 |
|---|---|---|
| 示例输入 | 单价 2.675，数量 1 | 分数 72.25，权重 1 |
| 原实现输出 | `2.67` | `72.2` |
| 独立修复后 | `2.68` | `72.3` |
| 完整验证 | **13/13 通过** | **15/15 通过** |
| 错误交换业务精度后 | 输出 `2.70`，**8/13 失败** | 输出 `72.2`，**9/15 失败** |

对照只在独立临时工作目录交换 `Decimal("0.01")` 与 `Decimal("0.1")`，其他源码与测试保持一致。这说明可复用的是有条件的计算原则，精度仍须绑定各自业务。合并后的两组原始测试证据仍为 11 项和 13 项；追加验证没有伪装成原任务证据。

## 修复了原实现的什么不足

原来的等价归并要求同一仓库、兼容域和代码目标，还要求完整条件相互蕴含。这适合合并同一项目的等价规则，不能直接表达不同业务中共同的修复原则。取消这些隔离检查会错误混合金额精度、分数阈值等具体行为。

新增 `backend/experience/principles.py`，将业务经验实例和共同原则分层保存：

1. 检查来源独立、验证成功、状态有效；使用明确命名空间，限制每次 2–5 个来源。
2. 通用归纳提示词只提供原始经验和结构化 schema，没有预填 Decimal 或目标合并答案。模型可返回共同原则、不同原则或证据不足。
3. 用 Pydantic 严格验证输出；核对每个来源的逐字证据和子问题位置；完整原始约束、依赖、异常及证据由程序附加，避免只依赖摘要。
4. 第二次独立上下文复核，有拒绝、缺失来源或不安全泛化就不落库。
5. SQLite 事务复核来源状态；重复同一操作复用结果，失败和中断保留状态且不自动重发付费请求。来源后续暂停或失效时，共同原则不可再检索。

新增 11 项回归覆盖伪造引用、来源遗漏、复核拒绝、错误条件、状态变化、命名空间隔离和幂等。全量后端 **648 通过、1 跳过**。

## 复现及适用边界

离线核对配置身份后，可以执行两项新任务；每次真实运行都会产生新的任务与经验 ID：

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/knowledge_live_experiment.py --inspect-api --llm-env-file .env
.\.venv\Scripts\python.exe -X utf8 scripts/demo_cross_business_tasks.py --live --llm-env-file .env --expect-api-identity <核查得到的身份>
.\.venv\Scripts\python.exe -X utf8 scripts/demo_cross_business_merge.py --run <上一命令输出目录> --llm-env-file .env --expect-api-identity <同一身份>
```

本次目录为 `.cache/cross-business-merge/20261114T144627Z-252034`。第二个脚本对同一来源与命名空间重复执行会复用已保存原则，仅重跑本地行为验证。

这是两个预先构造、真实运行的业务样例，不是对生产规模准确率的估计。原始提炼中包含对防止未来错误的条件性说明，不把每一条说明都计作实际发生过的独立故障。模型归纳和复核仍可能共同出错；目前按显式来源和命名空间启用，未改成全库自动后台调用，也未接入默认项目引用路径。用于新的第三个业务时，仍需核对适用条件并运行目标测试。
