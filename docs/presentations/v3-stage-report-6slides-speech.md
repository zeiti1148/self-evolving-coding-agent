更新日期：2026-11-02。原有 9 页版本保留。

## 第 1 页：项目目标与本阶段重点

大家好，我们的课题是《具备自演化能力的 Coding Agent 系统设计与实现》。系统已经具备分析问题、修改代码、运行测试和保存经验的基本闭环。本阶段在这个基础上推进了三个方向：第一，让一次复杂修复形成多条结构化经验；第二，让经验按仓库和适用条件受控复用；第三，引入多 Agent 协作，并补齐测试源码和代码差异的追溯能力。这里的自演化主要体现在经验的积累与后续利用，目前不涉及模型参数训练。接下来先介绍实现机制，再展示系统运行效果。

## 第 2 页：系统架构与修复闭环

技术栈继续采用 Python、FastAPI、SQLite 和 Vue 3。后端由 FastAPI 接收任务，Agent 核心循环负责决策，工具层负责读取文件、应用修改和执行命令。每个任务使用独立工作副本，并通过路径校验、命令白名单和超时控制限制操作范围。一个关键设计是：最终测试由程序独立执行，模型说修好了，并不直接等于任务成功。SQLite 保存任务、角色事件和经验，前端则展示执行过程、测试源码及代码 Diff。重启后可以查询历史记录，但被中断的任务不会自动继续修改代码。

## 第 3 页：经验演进与跨仓库复用

经验管理主要解决两个问题：怎样可靠地保存，以及怎样合理地复用。复杂样例的一次修复会直接提取姓名处理、数量校验和集合边界等三条经验，各自具有独立用途和适用条件，不是复制记录凑数量。保存时使用事务原子性，任何一条失败就整批回滚；通过请求幂等性，避免重复提交产生重复记录。检索统一限制为当前仓库经验和符合条件的已发布通用经验。项目经验必须经过通用化预览、编辑和显式发布，才能跨仓库使用。即使成功注入，目标项目仍要按自身业务规则测试，例如默认名称和数量范围可能不同。因此，检索命中、实际注入和修复通过需要分别记录。

## 第 4 页：多 Agent 协作与验证机制

多 Agent 模式采用诊断、修复和复核分工，每个角色使用独立上下文。当前包含两个诊断角色，分别查看代码并提出判断；修复角色根据诊断结果生成 Patch Proposal，也就是结构化修改提案；复核角色独立检查它是否满足业务约束。角色不能直接把修改写入项目，程序协调器会先核对文件的 SHA-256 快照。如果提案基于的文件已经变化，就拒绝这份过期提案。通过校验后统一应用修改，最终仍由程序运行测试。各角色共享步数和时间预算，角色事件和交接过程会持久化，便于定位失败原因。

## 第 5 页：验证结果与证据链

截至本次更新，后端全量回归有 537 项通过、1 项因本机不能创建真实符号链接而跳过；前端 107 项通过，类型检查和生产构建也通过。V3 验收的 13 个场景全部符合预期，覆盖仓库隔离、合并冲突、预算耗尽和保存失败等机制，另外还有过期提案等回归检查。其中一部分场景本来就应该停止或报错，所以不能理解成 13 次修复全部成功。新 Python 演示任务通过 18 项最终测试，生成 3 条经验；新旧两条任务的 6 个修改文件完成了哈希核对和重启检查。本轮使用脚本模型替代模型回复，API、SQLite、代码工具和测试均实际运行。此前已验证过真实模型基础闭环，但 V3 的真实模型效果仍需单独验证，也没有新增数据支持效率提升结论。

## 第 6 页：下一阶段：真实模型评测与检索优化

下一阶段有两项重点。首先用真实模型完整验证 V3，关注角色交接、修改提案质量，以及生成的多条经验是否独立、有依据、可复用。其次开展三组消融实验，比较无经验、完整经验和精简经验，统一模型、任务、参数和重复次数，记录成功率、工具调用次数、Token 用量及耗时，判断经验检索和压缩的实际价值。任务集会继续扩展跨文件关联与组合边界条件。团队可按 Agent 协作、评测样例、经验与展示三个模块分工，再交叉复核。下面切换到系统，现场演示协作过程、最终测试、修复前后 Diff，以及经验合并和通用发布。

## 术语备查（答疑用，无需逐条朗读）

- **事务原子性**：同一批经验全部保存或全部回滚。
- **幂等性**：相同请求重复提交，不重复生成记录。
- **独立上下文**：角色分别保留自己的输入与对话记录，通过明确的交接内容协作。
- **Patch Proposal**：由修复角色提交、交给程序校验和应用的结构化修改提案。
- **SHA-256 校验**：核对文件内容是否发生变化，用于识别过期提案和验证历史快照。
- **Diff**：展示修复前后增删的代码行及上下文。
- **消融实验**：在其余条件一致时，对比去掉或改变某个机制后的结果；本项目计划比较无经验、完整经验和精简经验。
