# Self-Evolving Coding Agent 架构设计

## 1. 项目目标

Self-Evolving Coding Agent 是一个面向 Java 代码修复任务的工程实践项目。用户提交任务后，系统调用兼容 OpenAI API 的大语言模型分析代码，自主选择受控工具修改项目并运行测试。修复成功后，系统从执行轨迹中提取结构化经验并保存，后续遇到相似任务时检索这些经验作为参考。

第一版以“任务提交—Agent 执行—工具操作—测试验证—经验保存—结果展示”的最小可运行闭环为目标，不追求复杂的自演化算法。

## 2. 技术架构

系统采用前后端分离的单体架构，降低三人协作和本地部署成本。

```text
Vue 3 + Vite Web 页面
          |
          | HTTP/JSON 轮询
          v
FastAPI API / 任务状态管理
          |
          | 后台调度同步 Agent
          v
Agent 核心循环 -----> OpenAI 兼容 LLM API
    |        |
    |        +------> 经验检索与保存 -----> SQLite
    v
受控工具系统 -----> Java 工作目录 / Maven + JUnit
```

- 后端运行时：Python 3.11+、FastAPI。
- 公共模型：Pydantic v2，供 API、Agent、工具和经验模块共同使用。
- Agent：项目自行实现同步的单 Agent 执行循环，不依赖 Agent 框架。
- 模型服务：通过兼容 OpenAI API 的接口接入，配置从环境变量读取。
- 前端：Vue 3 + Vite，第一版通过 HTTP 轮询查看任务过程和结果。
- 数据库：SQLite，用于保存任务元数据和结构化经验。
- 被修复项目：Java、Maven、JUnit。

## 3. 系统模块

### 3.1 `backend/agent/`

负责 LLM 接入、提示词组织、Agent 核心执行循环、工具调用调度、执行结果生成、经验提取与经验复用。该模块只能通过工具接口操作任务工作目录，不直接散落文件或命令操作逻辑。

### 3.2 `backend/tools/`

负责工作目录创建与清理、文件列表、文件读取、文件写入、受限命令执行、Maven 测试执行和工作目录边界检查。所有调用统一经过 `execute_tool` 并返回 `ToolResult`，避免 Agent 依赖具体工具的异常和输出格式。工作副本位于服务端配置的任务根目录内，原始测试项目始终只读。

### 3.3 `backend/experience/`

负责 SQLite 数据访问、经验保存、关键词/标签检索和经验列表查询。第一版采用简单结构化字段与文本匹配，不引入向量数据库。

### 3.4 `backend/api/`

负责 FastAPI 路由、请求校验、后台任务调度和响应序列化，向前端提供任务提交、状态/轨迹查询、结果查询和经验浏览入口。API 层不实现 Agent 决策逻辑。第一版使用单进程内存任务存储，并在 Agent 每完成一步时通过回调追加步骤，使轮询请求能够看到进行中的进度。

### 3.5 `backend/shared/`

保存 Pydantic v2 公共数据模型、枚举和统一错误码。该模块不依赖 Agent、工具、数据库或 FastAPI 的具体实现，其他后端模块均可单向依赖它。

### 3.6 `frontend/`

负责 Vue 页面，包括任务提交、Agent 执行步骤展示、最终结果展示和经验记录浏览。第一版优先保证信息可读，不建设复杂的可视化编辑器。

### 3.7 `benchmarks/java/`

存放可重复运行的 Java 缺陷样例。每个样例是独立 Maven 项目，用于联调工具调用、测试解析和 Agent 修复流程。

### 3.8 测试目录

- `backend/tests/`：后端公共模型和各模块的单元测试。
- 顶层 `tests/`：端到端测试，覆盖 API、Agent、工具和样例项目组成的完整闭环。

## 4. 三人开发分工

| 成员 | 主要目录 | 主要职责 |
| --- | --- | --- |
| 成员一（组长） | `backend/agent/`、`backend/api/` | LLM 接入、Agent 循环、工具调度、任务状态、经验提取/复用、后端 API、整体集成 |
| 成员二 | `backend/tools/` | 文件工具、命令与 Maven 测试工具、工作目录安全、统一执行结果 |
| 成员三 | `frontend/`、`backend/experience/` | Vue 前端、任务过程展示、SQLite 经验存储与检索、经验记录展示 |

公共数据结构和接口以 `docs/interfaces.md` 为协作契约。修改公共接口前应由三人确认。

## 5. Agent 执行流程

```text
接收并校验任务
      |
API 记录 pending 并后台调度同步 Agent
      |
工具模块创建隔离的 Java 工作副本
      |
检索相关历史经验
      |
构造上下文并请求 LLM
      |
解析下一步动作（工具调用或结束）
      |
通过 execute_tool 执行并记录 ToolCall / ToolResult
      |
步骤回调写入 API 内存任务存储，供前端轮询
      |
达到结束条件？ ---- 否 ----> 继续请求 LLM
      |
      是
      |
通过 execute_tool 调用 run_tests，记录并回调最终测试步骤
      |
仅在任务判定 succeeded 后尝试提取并保存经验
      |
形成 AgentResult 并更新任务状态，供 API 和前端查询
```

循环保持同步接口，并设置最大步数、命令超时和工作目录边界。Agent 只通过工具模块操作业务文件；工作目录的创建、校验和清理由工具模块负责。工具失败不应使服务进程崩溃，而应转换为结构化结果供 Agent 判断。最终是否成功以实际测试结果为依据。

### 5.1 模型决策预算与最终验证

- LLM 主动结束只表示请求结束，不能直接作为任务成功依据；Agent 必须完成最终测试才能确认修复成功。
- 每轮模型响应和工具结果进入下一轮上下文。工具失败可以反馈给模型，并在剩余预算内继续尝试。
- `max_steps` 统计模型决策轮数，同一响应中的工具调用第一版按顺序执行。达到上限后不得继续调用模型。
- 最终测试统一通过 `execute_tool` 调用 `run_tests`；必须记录 `ToolCall` 与 `ToolResult`，并将完整测试步骤通过同步回调提供给 API 查询。
- 最终测试不计入模型决策步数，但计入执行轨迹和 API 步骤数。达到上限后可以执行一次最终验证以记录测试事实，任务状态仍为 `stopped`。
- `tests_passed` 独立记录最终验证事实：`None` 表示验证未完成，`True` 表示通过，`False` 表示已执行但未通过。`failed/stopped` 不覆盖该事实。
- `succeeded` 必须同时满足 `repair_succeeded=True` 和 `tests_passed=True`。任何状态下声称修复成功都必须有最近一次成功的最终测试调用及结果作为证据。
- 最终测试之后代码再次变化时，旧结果不能作为最终成功证据，必须重新验证。公共模型保守地将测试后的 `write_file/run_command` 视为证据失效，只读操作不使证据失效。
- 经验提取或保存失败仅记录经验阶段错误，不影响已经验证成功的代码修复结果；`stopped/failed` 任务不产生成功经验。

## 6. 经验积累与复用流程

1. 在任务开始时，从任务描述、错误类型、技术栈和相关文件中提取简单查询条件。
2. 调用 `search_experiences` 获取少量相关经验，注入 LLM 上下文；经验是参考信息，不是必须执行的指令。
3. Agent 完成修复并通过测试后，从任务、根因、修改策略、验证方式和注意事项中生成结构化经验。
4. 调用 `save_experience` 持久化经验，并保留来源任务标识，便于追踪。经验提取、校验或保存失败会记录原因和 `experience_saved=False`，不生成虚假经验 ID，也不会把已经验证成功的代码修复改判为失败。
5. 后续任务通过关键词、标签和错误类型做基础检索；第一版不实现向量相似度。
6. 测试未通过、过程被取消或结果不确定时，不保存“成功经验”，避免污染经验库。

## 7. 公共技术决策

- 公共数据模型统一使用 Pydantic v2，并集中在 `backend/shared/`。
- `run_agent` 保持同步执行；API 层负责将其放入后台执行单元。
- 前端第一版通过 HTTP 轮询任务状态与已完成步骤，不使用 WebSocket 或 SSE。
- 工具模块拥有任务工作目录生命周期；Agent 不直接创建目录或读写业务文件。
- 原始测试项目只读，每项任务只修改服务端任务根目录内的隔离副本。
- 代码修复结果、最终测试结果和经验保存结果分别记录；经验存储失败不覆盖修复成功状态。
- 第一版任务状态与步骤可保存在单进程内存中。服务重启会丢失状态，无法跨进程或多 worker 共享，也不支持任务恢复，因此部署时只能使用一个 API 进程。后续如需多进程或可靠恢复，再迁移到持久化任务存储。

### 7.1 工作目录保留策略

- 每次 Agent 任务创建一个独立工作目录；仓库内的默认任务根目录为 `runtime/workspaces/`，也可以通过服务端配置放在仓库外。
- Agent 只能通过工具接口修改当前任务工作目录内的项目文件，原始测试项目保持只读。
- 任务成功、失败或停止后，第一版默认保留工作目录，用于检查代码修改结果和调试执行过程。
- 开发人员确认不再需要任务现场后，可以显式调用 `cleanup_workspace` 手动清理。
- 第一版不自动按时间删除工作目录；TTL 自动清理留待后续版本设计。
- `runtime/workspaces/` 和其他本地 Agent 工作目录属于运行时数据，必须被 `.gitignore` 排除，禁止提交到 GitHub。

## 8. 第一版功能范围

- 提交一个 Java 代码修复任务。
- 调用兼容 OpenAI API 的模型服务。
- 运行单 Agent、有限步数的工具调用循环。
- 在受控工作目录中查看、读取和写入文件。
- 执行受限命令及 Maven 测试。
- 保存任务状态、执行轨迹和成功经验。
- 通过简单文本/标签方式检索已有经验。
- Web 页面展示任务输入、执行步骤、测试结果和经验记录。
- 使用仓库内的小型 Maven 缺陷项目完成闭环验证。

## 9. 暂不实现的功能

- 多智能体协作、LangGraph 等编排框架。
- 向量数据库、嵌入模型和复杂语义检索。
- 自动训练、模型微调、在线强化学习或复杂自演化算法。
- 分布式任务队列、集群调度和多租户体系。
- 完整容器沙箱、操作系统级安全隔离和远程代码执行平台。
- IDE 插件、代码托管平台自动提交/合并和生产级权限系统。
- 复杂前端编辑器、实时协同和高级可视化。

这些能力需要在最小闭环稳定、风险和收益得到验证后再讨论引入。
