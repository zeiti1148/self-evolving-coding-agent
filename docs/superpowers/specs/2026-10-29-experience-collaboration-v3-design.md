# 经验演进 V3：多经验产出、多 Agent 协作与跨仓库复用

状态：待用户审阅；本次只完成设计与实施计划，尚未实现 V3。

## 1. 已确认目标和方案

用户要求先列出详细完整步骤，再逐步实施以下五项能力：经验合并、一个样例产生多条复杂经验、产品运行时多 Agent 协作、项目仓库经验隔离、跨仓库通用复用。

本设计将“多 Agent”解释为产品运行时协作，将“多个经验”解释为多条独立记录，不只是一个记录包含多个问题。推荐在现有架构上增量扩展，由协调器统一写入代码；这些属于工程方案，不冒充用户逐项确认。

考虑过的方案：

- **推荐：现有 Python/FastAPI/SQLite/Vue 上增量扩展。** 分析 Agent 可并行，修复 Agent 提交提案，协调器串行应用，验证阶段独立执行真实测试。复用现有工具边界，避免多个写入者互相覆盖。
- **未选：每个 Agent 独立工作副本、最后合并补丁。** 并发修复能力更强，但需新增补丁合并、工作副本生命周期和跨副本证据管理。本阶段不承担这些复杂度。

后续默认选择均为设计建议，不冒充用户逐项确认：保留单 Agent 模式；先支持同语言跨仓库；通用经验采用预览与显式发布；SQLite 做逻辑隔离；不引入向量数据库、队列服务或新 Agent 框架。

## 3. 总体流程和边界

登记项目 → 生成任务工作副本与来源指纹 → 按仓库检索 → 单 Agent 或多 Agent 修复 → 独立最终测试 → 一次批量经验提取 → 校验并事务保存 → 多经验详情 → 合并/通用化预览 → 显式发布通用记录 → 其他仓库检索与适配 → 真实测试及使用记录。

仍面向本地可信团队使用，一个 API 实例/进程。仓库隔离是自动检索、上下文及写入范围隔离，不等于多租户鉴权。经验管理页面可显式查看各登记仓库数据；产品若要支持不同用户之间的数据保密，需要另立身份与权限设计。

保留原始缺陷样例、测试/构建配置只读、受控工具、最终测试事实由程序产生的约束。零测试、跳过、超时、失败、预算耗尽均不能形成成功经验。模型输出、仓库文件和经验均为参考数据，不能提升工具权限。

## 4. 多条复杂经验

### 4.1 粒度与验收

一条经验是一套可独立检索的修复知识，包含症状、根因、解决步骤、适用条件、问题列表及顺序、涉及文件和真实测试证据。一个任务可以输出 1–5 条；不能为凑数复制相同内容，也不要求简单任务强制产生多条。

V3 的 Java/Python 两个新样例各设计 6 个可辨识缺陷，分成至少 3 组有独立用途的修复知识；每组至少包含 2 个相关问题。每个样例固定 18 项测试，涵盖失败输入、正常行为和组合调用。确定性验收要求每任务 3–5 条经验、其中至少 3 条含 2 个以上相关问题。真实模型验收使用同一标准；不达标真实报告失败，不由验收脚本补造经验。

提取仅在最终成功后发起一次模型请求，响应 `{experiences: [...]}`。每项的任务、仓库、语言、版本、测试证据、来源链和状态都由程序覆盖或生成。V3 新提取记录和可发布为 active 的记录必须绑定有效的独立最终测试。旧资料整理是例外：没有证据的 legacy_unreviewed 记录可以合并生成 V3，但仍是 legacy_unreviewed，不能注入或直接发布。多个记录可以引用同一次测试，但不得宣传成多次独立验证。

整批先校验再写入一个事务。任何记录非法、重复或数据库写失败，整批不落库；修复成功与经验保存失败分别报告。重复提交同一任务、同一规范化有效载荷返回原 ID；同一任务不同批次内容返回冲突，禁止无声覆盖。

### 4.2 兼容字段

- `schema_version` 支持 1/2/3；新增流程写 3，旧数据不伪造新证据。
- `AgentResult.experience_ids: list[str]` 默认空，每项校验为规范 UUID 字符串，与现有 ID 类型一致；保留 `experience_id`。新结果取数组第一项作为旧字段；旧结果读取时将已有单 ID 转换成单元素数组；两者冲突应报错。
- `batch_id: UUID | None`，用于批次追踪；旧记录为空。
- `reuse_status: active | candidate | legacy_unreviewed`。project 新记录为 active；未经发布的 global 为 candidate；无法证明来源/审核状态的旧 global 为 legacy_unreviewed。
- `derived_from: list[UUID]` 表示通用化来源，与合并的 `merged_from` 分开；程序填充，普通保存拒绝伪造。
- `supersedes_id: UUID | None` 表示通用发布修订替代的前版；程序校验并写入，不能由普通保存伪造。
- `required_capabilities: list[str]` 默认为空，精确匹配服务器登记的项目能力标识；不能使用自由文本条件直接充当可判定表达式。

## 5. 经验合并

保留 2–10 个不同来源、同语言、同 scope、同 repository_id、相容适用条件的现有规则。V3 还要求 reuse_status 与 required_capabilities 一致。candidate/legacy_unreviewed 可以在其各自状态内整理，但合并不会变成 active。

预览返回兼容性、具体冲突、新记录和直接来源。提交在事务中重新检查来源，不依赖旧预览结果；同源集合幂等；并发重叠合并仅允许一个消费来源。保留所有原记录，来源链无环；合并不额外运行模型，不自动把不同语义规则判成等价。

记录详情提供有界来源图（默认最多 100 个节点、深度 10，超出返回 truncated），可以沿 merged_from/derived_from 查看来源任务及证据。跨仓库专属经验不能直接合并；先分别通用化为同语言的相容通用记录，再合并。

## 6. 项目隔离与通用复用

### 6.1 隔离策略

所有生产检索使用统一策略：同仓库 active project + 同语言 active global；无 repository_id 时只允许 active global。其他仓库 project、candidate、legacy_unreviewed、被合并或发布修订替代的记录不能进入上下文。

仓库标识是登记文件中的稳定、大小写敏感字符串；多个子项目只有显式登记为相同 ID 才共享。客户端不得提交路径或自行指定身份。旧数据保持可读，无确切来源时不根据目录名字猜仓库。

公开经验查询是管理视图；Agent 检索是受约束使用视图，两者不可混用。单 Agent、各角色 Agent、失败后追加检索、验收及实验入口都需检查。自动任务缺少仓库身份时不得生成 global 成功经验，应保留修复结果并报告经验保存失败；手工通用发布只走专用流程。

### 6.2 通用化发布

1. 从 active、有真实证据的 project 经验选择来源；需要修订通用合并结果时，也允许选择当前有效、有真实证据的 global 合并结果作为新的通用化来源。
2. `promotion-preview` 提供可编辑草稿，移除具体文件路径、业务专有默认值和仓库名称，保留抽象前提及边界；首版确定性构造草稿，不额外请求模型。
3. 用户在页面补齐通用知识及适用条件，提交专用发布接口。服务端重新校验来源、内容、语言、状态与条件；专属路径/标识扫描只作为校验提示，不能宣称证明了语义通用性。
4. 生成新的 global/active 记录，保留 project 原记录和内部 derived_from；相同来源、载荷和前版引用的重复发布幂等。同一来源只允许一个当前发布版本；修改内容必须指定预览返回的 current_global_id 为 supersedes_id。事务检查此前版仍为当前版本，创建新记录及替代关系，使旧版停止自动注入；并发过期发布返回冲突，原记录仍可查询。不能直接修订已经参与合并的发布版本，应对其当前合并结果走重新通用化流程。
5. 目标项目的 capability 集必须覆盖 required_capabilities；自然语言 applicability 必须完整提供给目标 Agent，Agent 仍需检查具体业务语义并运行测试。

通用注入使用专用序列化：提供规则、适用条件、证据摘要及全局记录 ID，不向 B 的模型发送 A 的仓库路径、专属源码、来源任务描述或来源图。管理详情仍可追溯真实来源。对任意自由文本的人工通用化不能自动保证完全脱敏，应在发布预览中明确展示最终注入内容。

旧 global 保留可读，首次升级标记 legacy_unreviewed，不自动注入。旧资料经相同发布预览重新审阅后可生成 active global；没有结构化证据的旧资料需先在登记任务中重新验证，不能直接晋升。

首版只实现 Java → Java、Python → Python 的跨仓库复用。语言无关经验与跨语言代码迁移不在本阶段。

## 7. 运行时多 Agent

`execution_mode: single | multi` 默认 single，旧请求继续工作；新建任务页可以选择 multi。

角色与权限：

| 角色 | 输入与输出 | 权限 |
| --- | --- | --- |
| Coordinator（程序） | 任务状态、分工、共享预算、应用提案、汇总结果 | 唯一生产文件写入者；调用既有 ToolService |
| Diagnosis Agent（最多两个并行实例） | 同版本只读文件快照、失败事实、合规经验 → 问题和依赖建议 | 受控只读工具；独立模型客户端和上下文 |
| Repair Agent | 问题分组、最新快照、诊断摘要 → 文件修改提案 | 可读，不直接写文件或执行命令 |
| Review Agent | 提案、原文件、任务约束 → 接受/拒绝及简短原因 | 只读；独立上下文；不自报测试通过 |
| Verifier（程序） | 协调器应用后的工作副本 → 真实测试结果 | 独立调用现有 run_tests，不以 LLM 意见决定通过 |
| Experience Extractor | 通过后的轨迹 → 经验批次 | 单次无工具模型请求；无写源码权限 |

最多两个分析调用并行；其他阶段顺序执行。每个模型角色使用独立客户端，避免 deadline、messages 和 audit 共享导致串任务。共享内容限于任务事实、快照标识、问题列表、提案、结果摘要和经验 ID，不传隐藏思考过程。

PatchProposal 包含 proposal_id、agent_id、base_revision、changes[{path,before_sha256,content}]。协调器先验证所有路径和基线，禁止测试/配置修改。批次开始前保存允许文件的原内容；部分应用失败尝试恢复并记录恢复结果；恢复失败即终止任务，不继续验证或产出经验。审计记录实际每次写入及失败，不能把应用失败冒充完整提交。

并行诊断期间冻结任务写入。过期提案必须拒绝并重新读取最新快照，不能覆盖其他已应用变更。同文件提案顺序整合；无意义重复提案受预算限制，不无限重试。评审拒绝返回 Repair Agent；最终测试失败则把真实失败事实交回修复阶段。

max_steps 保留默认 20、上限 100，多 Agent 的诊断/修复/评审模型调用共同消费该预算；通过锁在调用前占用预算，不按角色倍增。独立最终测试不消费决策次数；成功后经验提取最多额外一次，仍受整任务截止时间限制。默认总时限沿用 600 秒。重试、耗时、提供商 token（若有）分角色记录，不能把未报告用量填成零。

新增角色事件与工具步骤分开存储，工具步骤依然保持连续序号和真实一一对应 call/result。服务重启将父任务及未结束角色标为 stopped，保留已完成事实，不自动续跑。

## 8. 验收与交付

每一步提供有针对性的失败测试、实现和通过结果；旧兼容性与端到端链路最后全量复验。定量目标：

- 两种语言各一个 V3 样例，18 项测试全部通过，产出 3–5 条经验，其中至少 3 条有 2 个相关问题。
- 同一生产任务至少有诊断、修复、评审三个独立角色的真实调用和交接记录，最终测试由程序执行；脚本模型和真实模型分别标记。
- 合并前预览、冲突拒绝、重试幂等、并发不重复消费、来源可追溯。
- A 专属经验不出现在 B 的任何角色模型请求；candidate、legacy_unreviewed 不自动注入。
- A 经验发布为通用后，B 同语言的独立样例任务实际收到通用规则并通过测试；原 A 专属记录仍未注入。能力不符、语言不同、业务语义冲突的负例不被自动套用。
- 任务重启、旧库读取、经验链接、多个 ID 展示、预算耗尽和保存失败有明确结果。

最终交付设计、计划、代码、迁移、测试、V3 验收脚本、独立报告与演示步骤。报告区分“已检索”“已注入”“修复成功”，不把它们直接当作效率提升。效果评估需冻结训练库与目标库，控制同一任务预算并记录用量，未做配对实验就不宣称多 Agent 更快或更省。

回退：切回 single 模式、关闭通用注入；数据库变更采用新增表/兼容字段，升级前备份 SQLite，旧程序回退须使用匹配版本备份（旧 Literal[1,2] 不能直接读取 V3），不删除运行数据。
