# V3 按当前失败证据检索

## 目标与证据

用户要求先扩大 Java/Python 实验，再解释检索收益并针对性优化。扩展基线 108 项均已完成且通过最终测试，整个批次运行时代码保持不变。轨迹和代码检查显示：候选池仅 Java 1 条、Python 3 条，36/36 组配对的首次参考集合相同；大量任务直接根据明确需求完成修复，尚无失败反馈时即反复携带经验。现有查询向前查找失败测试，会跳过其后的成功测试，异常集合也持续累积。

最终完整统计写入扩展报告；这里固定待验证的机制和设计，不用评估目标的默认值、文件名或标准修复制定检索规则。

## 方案选择

- 增大词法权重：候选数小于 Top-5，无法解决无关时机仍注入全部经验的问题。
- 继续删减规则文本：可能损失适用条件，且总用量还包含修复轨迹和提取阶段。
- **选择当前证据驱动的启停。** 保留原有规则和排序，先判断当前是否存在需要经验的具体失败；通过测试后撤下历史失败参考。

这是执行者根据数据作出的实现选择，用户已要求直接分析并优化。

## 行为

新增 `adaptive` 策略，保留 `baseline`、`contextual` 的行为和实验入口。

1. 尚未运行测试：任务描述出现可识别的具体异常类型时允许检索；否则暂不注入。
2. 最近一次测试失败：仅使用该次失败的错误类型与上下文，加任务说明构建有界查询。不得因历史失败扩张当前异常集合。
3. 最近一次测试成功：不再注入旧失败经验。后续再次失败时恢复检索。
4. 工具执行、权限或环境错误不能伪装成测试失败证据。
5. 每次模型调用仍重新检查语言、仓库、发布状态、能力和异常硬过滤；full/compact 保留现有表示与全部适用条件。
6. single/multi 共享证据判断。跳过、启用与测试已通过的原因写入检索审计，不保存完整查询或密钥。

`reference_received=false` 在 adaptive 下可能是合法的策略结果，必须在报告中如实显示，不能把未注入的任务称为已使用经验。

## 接口与测试

- `backend/experience/retrieval.py`：共享异常解析（保持原语义）及 `adaptive_retrieval_evidence(task_description, results, language)`，返回 query、error_types、reason；query 为 None 表示不检索。
- Agent 与 coordinator：新增策略分支，旧策略不改；可按 `EXPERIENCE_RETRIEVAL_STRATEGY` 配置 API 默认策略。
- 评估 CLI 接受 adaptive；同一冻结库、六案例、三重复、三表示复验 54 项。
- 回归覆盖：无证据不注入、任务已有具体异常、失败触发、当前异常替换历史异常、成功清除、环境错误不触发、再次失败恢复、语言/仓库/能力限制保持，以及多角色接入。
- 原有 Agent 构造默认值保留兼容；应用设置可选 adaptive。是否采用新应用默认值以完整复验结果与回归测试为依据。

## 解释边界

新策略可能减少经验提前提供帮助的机会，尤其在任务描述模糊而测试尚未运行时。保留旧策略作为配置回退。复验必须同时报告成功率、实际经验注入覆盖、修复阶段与提取阶段用量；前后分批运行仍有时间顺序混杂。

六个仓库仍属于输入处理任务，不能据此声称复杂仓库修复能力提高。若修复成功率保持而用量下降，只能报告本测试集合中的开销改进。
