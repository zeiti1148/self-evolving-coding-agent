# 阶段五改进设计：覆盖、适配、成本与证据

日期：2026-11-21。来源：《中级实训》阶段四「存在的不足与后续工作」五条。

本设计只描述要做什么、边界在哪、怎么验收，不预先宣称收益。每条改进都以当前代码与实测数据为依据，无法验证的部分明确写为未知。

## 总原则

- 保留「上传项目 → 真实修复 → 独立测试 → 经验提取 → 自动比较 → 合并/冲突 → 后续复用」主链路，不新增实验专用入口。
- 不引入需要额外部署的服务；仍然只用 Python/FastAPI/SQLite/Vue。
- 任何"更省钱/更准"的说法都必须有本机实测对照，不能用作者宣称替代。
- 无法自动判定时保持 needs_review，不用猜测换取覆盖率。

## 一、自动比较的覆盖与成本

### 现状（核实于 2026-11-21）

- `backend/experience/automation.py:15` 定义 `MAX_CANDIDATES = 5`；`_plan()` 统计了 `candidate_total`（同文件 83、119 行），但只把排序后的前 5 个候选入队（106 行）。
- 候选排序信号为 `(RRF 词法排名, 错误类型交集, created_at, id)`（100–102 行），没有语义或符号级信号。
- 每次 `process()` 只处理一对模型比较就 `break`（237–238 行），因此成本上限 = 对数 × 1 次模型调用。
- 未被选中的候选不会补查：`candidates` 列只存已选 5 条，重启后仍以 `candidates is not None` 跳过 `_plan()`（172–173 行）。
- 本机 `data/app.db` 有 31 条经验，但没有 `experience_auto_jobs` 表，说明该库从未运行过自动比较；本阶段需要先制造可复现的对照数据。

### 设计

1. **候选盘点（只读）**：新增接口与页面列显示「同语言同范围候选总数 / 已比较 / 本次入队 / 剩余未比较」，数据全部来自现有 `experiences` 与 `experience_auto_pairs`，不新增业务表。
2. **分批补查**：`_plan()` 改为按 `MAX_CANDIDATES` 分批取未比较候选（以 `experience_auto_pairs` 的 `(left_id,right_id)` 唯一约束判定"已比较"），job 未完成时保持 `pending` 并交给现有 lease 继续领取。预算上限由 `MAX_PAIRS_PER_JOB` 显式限制，超过上限时 job 置为 `succeeded` 并在提示中写明"剩余 N 对已推迟"。
3. **候选排序评测**：新增离线脚本，对固定用例集比较若干排序策略（词法 RRF、错误类型、文件/符号交集、可选语义排序）的 recall@1/@5 与误合并率。排序目标是"把真等价对排进前 5"，不是"提高相似度分数"。
4. **漏合并案例集**：`benchmarks/missed-merge/*.json` 记录已确认的漏合并（来源对、期望关系、发现途径、日期、是否仍需人工确认）。重放只跑确定性逻辑，不调用模型；真实模型结论单独标注。

### 验收

- 候选盘点数字与数据库计数逐项一致。
- 构造 12 对以上候选（含 >5 对同范围同语言）时，第二批之后确实被比较，且总模型调用次数等于 `ceil(对数/5)` 且不超过 `MAX_PAIRS_PER_JOB`。
- 排序评测给出每个策略的 recall@5 与误合并数，并明确样本量不足处不下结论。
- 漏合并案例集重放全部通过，且新增一条"已修复的历史漏合并"回归。

### 非目标

- 不追求"全部候选都调用模型"；覆盖率提升必须在预算内。
- 不因为相似度高就自动判等价（等价仍需现有证据与复核路径）。

## 二、冲突验证的语言与工程适配

### 现状

- `backend/api/conflict_verification.py:105` 明确 `not general and project.language != 'python'` 即拒绝；`verify()` 进一步要求目标路径以 `.py` 结尾（155 行）并用 Python `ast` 定位函数（27–34 行）与拼接（53–82 行）。
- 执行与证据采集已支持多语言：Surefire XML（211–212）、CTest XML（213–214）、`go test -json`（227–236）。因此缺口只在"目标映射 + 实现拼接"，不在执行。
- `backend/experience/grounding.py:5–14` 已用 tree-sitter 支持 python/java 的符号提取；Go/C++ 返回空集合退化为文件范围。
- 2026-11-21 核实 PyPI：`tree-sitter-go 0.25.0`、`tree-sitter-cpp 0.23.4`、`tree-sitter-java 0.23.5` 均有 `win_amd64` wheel。

### 设计

1. 抽出 `backend/experience/transplant.py`，统一三个能力：`locate(源码, 语言, 限定名)`、`signature(...)`、`splice(目标, 供体, 限定名)`。Python 沿用现有 AST 实现（行为不变），Java/Go/C++ 用 tree-sitter 节点字节区间拼接。
2. 语言能力矩阵显式声明支持级别；未支持或无法唯一定位时抛 `VerificationUnavailable`，保持「需人工确认」，不得降级成"不冲突"。
3. 隔离执行复用 `WorkspaceManager` + `ToolService`（已有多语言实现），只补拒绝理由与证据字段的语义。
4. 至少一个真实工程反例（Java 方法、Go 函数、C++ 方法各一）用于验证"能定位 → 能判定"与"不能定位 → 必须拒绝"两条路径。

### 验收

- 三种语言各有一组：交换实现后双侧测试通过/失败可区分；签名不同、依赖辅助函数不同、宏/模板不可解析时明确拒绝。
- 本机缺少 cmake 时 C++ 用例 skip 而不是 fail；跳过原因写入报告。
- 现有 Python 用例行为不变（回归全绿）。

### 已知限制

- C++ 宏展开、模板特化和多文件接口不在自动拼接范围内，一律转人工。
- 跨服务/外部依赖无法在单机隔离副本复现，这类冲突不自动裁决。

## 三、自适应检索的成本

### 现状

- `backend/agent/core.py:86/93` 固定 `limit=5`；`backend/experience/retrieval.py:26–27` 默认 `character_budget=16000`。
- 自适应只在"最近一次测试失败"时给查询，测试通过或执行错误时不注入（`retrieval_evidence.py:32–51`）。
- 一旦发现新的错误类型，`update_references()` 会重新检索并整包替换参考经验（`core.py:113–129`），跨轮次没有按规则身份去重。
- 现有评测：`scripts/experiment_v3.py` 默认 dry-run 打印 324 个计划任务；真实对照受预算限制。

### 设计

1. 跨轮次注入去重：以 `rule_id` 为准，后续轮次只追加新增规则，不重复发送已注入内容。
2. 预算参数化：`limit` 与 `character_budget` 按检索策略取值并写入任务审计（注入规则数、字符数、是否随新一轮变化）。
3. 引用追踪：记录模型实际是否引用被注入规则（从审计消息中解析），用于计算"注入但未被使用"的比例。
4. 评测先离线：用固定经验库 + 计划任务做 dry-run 与确定性部分；真实调用只跑小样本（建议 6 对 × 2 策略），结论限定在样本内。

### 验收

- 同一任务多轮检索时，注入集合单调增加且无重复 `rule_id`。
- 审计字段可导出为对比表：策略、注入规则数、注入字符数、耗时、token、最终测试结果。
- 至少一组对照明确写出"未测出成本优势"或"测出优势"的边界条件，不允许外推。

## 四、自动判定的证据强度

### 现状

- `backend/experience/reviews.py` 已支持 `resolve` / `reopen` / `history`，自动决定的证据存放在 `automatic_resolution` 字段且服务端专属（48–59 行）。
- `backend/experience/recovery.py` 已有授权（grant）、`confirm`、`enqueue` 与基于哈希的有效性校验，源码或测试配置变化会让授权失效。
- 冲突交叉验证会重复两轮交叉测试（`conflict_verification.py:182–187`），但"测试覆盖到什么程度"没有被记录为证据等级。

### 设计

1. 证据清单：把一次自动决定引用的证据展开成可读清单（来源任务、最终测试数、原始失败、交叉测试轮次与结果、覆盖缺口提示）。只展示事实，不生成测试。
2. 误合并撤销：新增撤销入口，复用 `reopen` 与现有依赖失效传播，保证撤销后相关授权立即不可用、原始经验不变。
3. 失效重验：源码、测试配置或来源关系变化时，把相关授权标记为需重验并进入现有补证队列；不自动恢复。

### 验收

- 撤销一条已自动合并的规则后，检索不再返回该规则，依赖它的授权全部失效，历史记录保留。
- 来源源码变化后，授权自动进入待重验，且不会在重验前被注入。
- 证据清单与数据库字段逐项一致，页面不出现无法追溯的结论。

### 非目标

- 不自动生成新的边界/异常测试，也不把"模型声称覆盖"当作证据。

## 五、使用体验与资料维护

- 页面：候选盘点与补查进度、批量补证入口、失败原因与重试状态、大规模经验检索的分页与筛选。
- 文档：阶段五进展直接更新本仓库 `docs/`；实验明细、源码说明与汇报材料分开保存，不混写为同一结论。
- 团队：扩大真实工程样本，交叉复现记录单独归档。

## 数据与接口影响

- 新增列/表仅限于自动比较的分批状态（`cursor` 或等价字段）与取消合并审计，均可幂等迁移。
- 对外接口保持向后兼容：新增只读盘点字段，不改变现有字段语义。
- 可选依赖：若采用 tree-sitter 的 Go/C++ 语法包，写入 `requirements-semantic.txt`，不进入基础依赖。

## 明确的未知

- 分批补查能把漏合并降低多少，取决于本机能否积累足够多的同范围经验；样本不足时只能报告方向性结论。
- 语义排序是否值得引入取决于 CPU 上的实际延迟与收益，需实测后再决定。
- 每条改进对修复成功率的实际影响未知，本轮不宣称提升。
