## 具体恢复与迁移约定

原始 ID 和历史内容不变；规范规则、证据关联、候选索引和作业可以重建。增量迁移回填目标索引及执行前置边，旧来源级冲突保留独立审计。全记录合并/发布会检查子规则，不能借新 ID 重新启用暂停的规则。

作业五次失败后显示 failed，可通过页面重试。正在运行的租约不会被抢占，过期 worker 的成功或失败回调都不能覆盖新拥有者。原始保存成功但派生失败是明确可观测的两种状态。相同证据键却出现不同内容会进入 needs_review，不能只靠重试解除。

unknown 表示关系不确定，不能称为真实矛盾；若同次检索会同时命中未知重叠规则，系统省略相关组合。人工确认等价与兼容分别建审计决定。旧 V3 多问题正文可能包含共同限制，因此保守地整组引用；V4 可显式拆分前置规则和独立规则。

语义策略变更、模型清单或校准变化都会重新排队。模型加载只读本地快照，推理不持有 SQLite 写锁；替换模型清单后会清除旧模型对象与概率缓存。没有可用校准时，精确去重、后台整理及人工审阅仍可使用。

## 官方与 GitHub 依据

核查日期：2026-11-14。以下是采用的方法依据，不能替代本项目实验。

- [Sentence Transformers](https://github.com/huggingface/sentence-transformers) 与 [E5 模型卡](https://huggingface.co/intfloat/multilingual-e5-small)：多语言向量召回、query/passage 前缀和长文本分块。相似度不授权等价。

- [Python 比较表达式](https://docs.python.org/3/reference/expressions.html#comparisons)：代码比较具有精确操作语义。R15 在推断之外保护比较事实，宁可放弃同义自动合并。
- [graphlib](https://docs.python.org/3/library/graphlib.html)：明确依赖的拓扑排序和环检测。
- [Hypothesis 状态机](https://hypothesis.readthedocs.io/en/latest/stateful.html)：组合保存、整理、决定、撤销的不变量测试。

## 实验设计

1. **离线语义**：600 对受控规则，精确重复、同义、互补、冲突、不同版本和未知条件各 100 对。开发 306 对、保留 294 对，按语言模板隔离；比较冻结旧策略、确定性新策略、加 E5、加 NLI。另加 16 对否定、顺序、数值比较及超长输入反例，作为发布门槛而非继续调阈值。
2. **组与故障**：40 组工作流实验，含 20 次重复、61 条组、大小写、版本、顶层限制、局部暂停、依赖和撤销；回归另覆盖事务失败、租约、并发、恢复、旧记录迁移。Hypothesis 为 20 组、每组最多 20 步状态操作。
3. **容量**：100/1000/10000 条单文件范围互不重叠的经验，测原始保存 P50/P95、队列完成时间、检索延迟、数据库字节、记录/证据数及完整性。稠密范围的平方级比较成本单列，不混作稀疏容量结果。
4. **真实修复**：12 项训练（Java/Python 各 6）产生 9 条可保存经验；4 项 Java 提取失败，不补造经验、不重跑训练。8 个评估项目（每种语言各 4）× 无经验/旧策略/新策略 × 4 次，共 96 次；总计 108 次，20 步/600 秒，三个工作线程。场景含条件默认值、同文件独立函数、版本边界、显式依赖。
5. **隔离及统计**：相同修复器、提供商和项目测试；所有原项目未变。训练库冻结后评估输出写入另一个库；旧、新快照运行前后 SHA-256 一致。条件顺序轮换，独立保留测试在修复后才运行。记录提供商 token 覆盖率和置信区间；小样本、重复模板及同时运行任务的时延噪声均明确说明。
6. **最终代码核验**：真实模型运行期间继续修复了边界情况，因此启动时文件哈希不能单独代表全部延迟导入模块。最终代码另存完整快照，以真实运行的冻结资料和全部新策略查询重放，检查引用是否一致，再重跑 40 组和容量。此重放不追加付费模型调用，也不伪装成新的真实修复实验。

## 保留的实际限制

- 受控模板及小项目较简单，不能由满分推断真实仓库的修复成功率会提高。真实实验若出现天花板效应，应报告没有测出提升。
- 模型无法证明隐含业务条件；约束提取仍可能遗漏事实。没有共享条件依据时只能待审阅，冲突召回与自动覆盖率必须同时报告。
- 1 万条稀疏数据可以完成整理，但单机 SQLite 的密集规则比较、全库向量排序和大范围读仍有成本。性能指标为本机实测，不承诺其他机器或稠密数据。
- 模型权重不纳入 Git；新环境先安装可选依赖并下载固定 revision，再运行校准。没有这些步骤时系统使用确定性处理。

## R38：同一代码目标在不同上传版本中的经验冲突被漏检

真实反例来自 [pytest #10447](https://github.com/pytest-dev/pytest/issues/10447)：distutils 的子类 fixture 依赖父类初始化，pytest 7.2 的继承标记顺序却使子类先执行。上游 [#11155](https://github.com/pytest-dev/pytest/pull/11155) 调整了顺序。此前正常流程提取的 pytest 经验广泛建议正向 MRO、子类优先；新缺陷正好检验这一经验的适用边界。

不足：上传项目以内容哈希区分仓库和兼容版本，已有规则维护只比较相同仓库及兼容键。跨上传自动归纳能拒绝不安全合并，却不会将互斥要求登记为正式冲突，因此用户无法看到冲突、暂停复用和处理历史。

具体方案：

- 在正常自动比较队列的共同原则归纳之前，增加跨上传冲突检查。只对不同任务中具有相同已落地 `文件#限定符号` 的问题对调用模型；单纯文件相同、语言相同或措辞相似不够。
- 判断真正重叠的适用条件及互斥行为。上传 ID、修订哈希不同并不自动使宽泛经验的作用域互斥；有明确不同业务合同或版本边界时，也不能仅凭代码目标相同就判冲突。
- 复用 Pydantic 严格结构校验、逐字原文核验和一次独立模型复核。问题索引、候选目标、双方解决方案引文及复核覆盖由程序校验，缺少任何依据不发布冲突。
- 复用 SQLite 事务、唯一规则对、队列租约和现有 `knowledge_relations`。发布前重新核对原始快照与资格；冲突和队列结果在同一事务提交，禁止覆盖已有人工决定。模型提议、复核和请求审计持久保存，失败不会自动重复付费。
- 冲突进入既有审阅界面和规则暂停机制；依赖被争议来源的共同原则立即失去可复用资格。处理选中的规则后，队列恢复资格检查，原始经验、原验收结果和既有历史均不改写。
- 正常经验页显示双方互斥原文、共同适用条件、独立复核、处理前后状态及决策依据；按任一来源仓库筛选都能找到跨上传冲突。未增加实验路由。

新增 12 项受控回归覆盖正常队列发现/处理、作用域不同、复核不同意、伪造引文、错误目标、缺失复核、租约失效、资格/内容变化、无符号零调用、失败审计及旧共同原则失效。受控响应仅用于隔离测试数据库，真实模型运行另存完整实录。

## R39：真实独立复核暴露的问题编号歧义与重试审计缺口

## R73：恢复资格检查在目录中反复扫描文件

重启主应用验收时，真实经验目录出现 503，后台队列也记录存储等待错误。只读性能剖析定位到：同一请求中，目录先计算全部恢复授权，再对每张卡片重复计算和检查文件。13 张卡片触发 44 次完整文件校验，剖析耗时 10.68 秒，其中 9.57 秒用于文件验证。长读事务拖延写入提交，随后读取也可能等待；这与 [SQLite 回滚日志模式的锁机制](https://www.sqlite.org/lockingv3.html) 一致。

修复为在同一个请求、同一数据库快照内计算一次完整验证结果及可用授权，供目录和恢复历史展示复用。仍逐次检查文件，不做跨请求缓存，不跳过模型检索边界上的重新验证。相同真实库的完整校验降至 4 次，剖析耗时降至 0.88 秒。补充测试确认下一次请求中文件变化立即使授权失效。

此优化在上述 999 项全量检查所加载的版本之后完成，另跑目录、恢复、共享约束 45 项，以及 API 与上传后自动归并流程 11 项，均通过。主应用重启后目录 HTTP 返回 200，实测约 425 毫秒；任务指标接口约 84 毫秒。原 10 条经验、4 项恢复及授权、冲突审阅和暂停记录的摘要核对未变。

## R80：自动比较列表重复验证恢复授权，超过页面超时限制

2026-11-16，用户反馈“自动比较与合并”经常请求超时。对正式数据库的在线备份进行性能剖析：默认 5 条记录、12 项变化，需要反复读取每份来源及规则溯源；各层分别重新计算全部恢复授权，导致 4 份授权累计执行 44 次完整证据文件校验，耗时 22.52 秒，超过页面 15 秒的请求限制。来源、溯源和审阅历史还会在外层读事务内打开其他连接。后台同时记录队列存储等待失败；长读事务会增加回滚日志模式下写入的等待，机制参见 [SQLite 隔离说明](https://www.sqlite.org/isolation.html)。
